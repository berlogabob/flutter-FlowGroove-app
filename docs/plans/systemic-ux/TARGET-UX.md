# FlowGroove — целевая UX-модель, вариант для проверки

Статус: предложение на основе системного аудита 23 октября 2026. Не утверждённый редизайн, не реализация. Исходные F-001—F-009 сохранены как UX-001—UX-009 в BASELINE.md/activity.json; активный порядок работ — PLAN.md.

## 1. Что именно меняем

Не новую тему и не аудиодвижок. Меняем правила: где пользователь находится, что за объект открыт, какое действие основное, как сменить материал и куда возвращает Back. Сохраняем Mono Pulse и существующие сущности Song, Band, Setlist, Lab entry, task, session.

### Единый словарь

- Song — объект материала. Открытие не равно редактированию.
- Sheet — представление нот/текста/структуры, не отдельная копия песни.
- Materials — существующие Lab entries: MIDI/audio/ссылки/заметки. Переименование Lab проверяем, а не считаем обязательным.
- Practice — выполнение занятия с материалом и транспортом.
- Progress/History — журнал и статистика занятий; не притворяется транспортом.
- Metronome — инструмент/часть Practice, а не неочевидное имя всего MIDI workspace.
- Edit song / Edit entry details / Edit MIDI notes / Edit arrangement — разные операции. Одного универсального Edit без контекста недостаточно.

## 2. Навигация: минимальная основная альтернатива A

Сохранить корневые Home · Songs · Bands · Setlists. Пятый слот More становится стабильным глобальным разделом, а не меняющимся меню текущей библиотеки.

```text
Home
  Continue / Start practice
  Recent material
  краткое Progress summary
Songs
  Search/filter → Song overview
  Add song
Bands
  Band overview → Songs / Setlists / Rehearsals / Members
Setlists
  Setlist overview → Play / Edit / Export
More (одинаковый набор из любого корня)
  Tools: Metronome, Tuner, Recorder
  Progress / history
  Profile / Settings / Support
```

Импорт/экспорт/дубликаты/фильтры принадлежат Songs/Setlists, не глобальному More. Команды песни принадлежат песне, команды группы — группе. Глобальный и объектный overflow не должны выглядеть как одна вкладка с непредсказуемым содержимым.

Существующий нижний режим `[Back] [title / primary action] [object menu]` можно сохранить на первом этапе. Нет доказательств, что ради исправления надо немедленно заменить его стандартным верхним AppBar. Контекст объекта при этом должен быть понятен и в содержимом экрана; длинное название не должно быть единственным ориентиром, спрятанным в обрезанном нижнем слоте.

### Альтернатива B — только для сравнительного теста

Отдельный корневой Practice вместо части Home; Songs/Setlists под общим Library — лишь если task tests подтверждают удобство и не ухудшают быстрый концертный доступ к сетлистам. Не вводить Library ради меньшего числа вкладок. Никакого универсального «максимум 7 пунктов» из закона Миллера.

## 3. Контракт каждого семейства экранов

### Список

Поиск/фильтр → понятный scope Personal/Band → карточки одинакового устройства. Нажатие карточки — открыть объект. Отдельный action — create; у него есть accessible name. Действия Edit/Delete/Export — в явном контексте. Нельзя открывать одну сущность для просмотра, другую сразу как случайную форму редактирования без объяснения.

### Обзор песни

- Название, автор, источник/группа; основные BPM/key — кратко.
- Основное действие Practice; рядом Sheet, Materials, Tasks.
- Edit song — явная команда; полный редактор уже существует.
- Из Materials можно просмотреть конкретный файл, перейти к партии/занятию или явно редактировать нужный уровень. Открытие MIDI не должно подразумевать, что пользователь хотел именно Mixer.

### Рабочее пространство Practice

- Контекст: Song · source · instrument/part · passage. Показывать только реально известные значения, не выдумывать последний диапазон.
- Компактный transport/tempo; гигантский свободный tempo dial может остаться в отдельном Metronome tool, но не вытеснять основной материал занятия.
- Постоянный Source/Backing selector при MIDI, drums и пустом состоянии. Hide panel не заменяет смену источника.
- Материал/партия/фрагмент → Loop/repeat, speed, count-in; использовать уже существующие возможности. В текущем launchpad Loop есть.
- Представление, выбор партии, mute/solo, замена материала и редактирование — независимые намерения; визуальный переключатель не должен незаметно менять источник/звук.
- Notes/tasks/record — вспомогательные действия, не отдельная потеря рабочего контекста.
- Resume восстанавливает подготовку, но не включает воспроизведение автоматически.
- Сначала сверить существующую модель session/context; не добавлять второй набор глобальных providers «для нового Practice».

### Сетлист

Название/scope → порядок и доступность песен → Play. Edit отдельно. Если доступно 2 из 6: сообщить это до старта, сохранить все шесть ссылок и порядок, предложить безопасное выяснение причины. Не удалять четыре недоступных записи автоматически. Для недостаточных прав не показывать закрытые данные.

### Группа и репетиция

Band overview — единый scope для songs/setlists/rehearsals/members. При переходе к песне или инструменту scope остаётся видимым. В репетиции отделить подготовку, открытие материала и административное редактирование. Ролевые ограничения проверяются на тестовых аккаунтах, а не сменой прав текущего пользователя.

### Recorder, Tuner, Settings

Recorder: до записи понятен scope (свободная запись или материал), после — безопасное сохранение/отмена; не менять существующий workflow до проверки.
Tuner: различать Listen mode и Start listening, подписать компактные действия и проверить большой шрифт; не включать микрофон без понятного действия.
Settings: одинаково доступен через More; текущие значения видимы; beta light не выдавать за полностью проверенную тему.

## 4. Сквозные user flows

### Начать / продолжить занятие

```text
Home → Continue (если контекст достоверен)
     → проверить Song / source / part / passage / tempo
     → Practice → Play (только явное действие)

или Home / Song overview → Start practice
     → выбрать недостающий материал / партию
     → настроить фрагмент / Loop → Play
```

Выход и возврат не должны требовать повторного поиска материала. «Resume работает» — проверяется отдельно на persisted полях и human recognition, не по факту наличия кнопки.

### Посмотреть, затем изменить песню

```text
Songs → Song overview → Sheet / Materials / Tasks
                    → Edit song → Save или Cancel
```

Cancel/Back одинаково различают отсутствие изменений и dirty draft; восстановление формы и unsaved warning тестируются на безопасной копии, не на рабочей песне пользователя.

### Подготовить и открыть сетлист

```text
Setlists → Setlist view → review unavailable (если есть)
                       → Play available songs → queue с явным составом
                       → Edit (отдельно, с сохранением исходных ссылок)
```

### Выполнить задание

```text
Home/Progress → Task → связанный материал и доступный контекст
                    → Practice → вернуться к задаче / заметке
```

Контекст секции/партии показывается только если существует в модели. Старые задания без этих полей остаются валидными, а не теряются при миграции.

## 5. Общие UI-правила, сохраняющие Mono Pulse

- В каждом состоянии понятны объект, scope, основное действие и путь назад.
- Оранжевый — приоритет/активность; статусные и музыкальные цвета остаются разрешёнными исключениями, а не новым набором брендов.
- Единые роли title/body/metadata/caption; не один размер для всего и не автоматическая замена каждого локального TextStyle.
- Контролы одной задачи сгруппированы, дополнительные настройки раскрываются по мере необходимости. Главное действие не теряется за метаданными/большим декоративным контролом.
- Create/Edit/View/Play различимы; delete не маскируется под обычный шаг.
- Loading / empty / partial / error / permission-denied — разные состояния с разным действием восстановления. Переиспользовать уже существующие ErrorBanner/loading/cached patterns.
- Каждый icon-only action имеет имя; большие шрифты, screen reader и light проверяются отдельно. Никакой общей декларации WCAG по скриншотам.

## 6. Проверка до реализации

Сравнить текущий вариант и low-fi A на задачах: начать с нужной партии; сменить источник без скрытия текущего; посмотреть песню без редактирования; понять состав частично недоступного сетлиста; найти Settings из другой корневой вкладки; продолжить предыдущую подготовку.

Фиксировать человеческий результат без подсказки, ошибки/возвраты, уверенность и короткую оценку лёгкости. Скриптовые шаги и секунды хранятся отдельно от human task success. Макеты `target-wireframes.*` — иллюстрация A, не доказательство его превосходства.

## 7. Порядок реализации после утверждения

1. Утвердить контракты и выбрать один thin slice; не весь редизайн за раз.
2. F-006 (постоянный Source selector) + F-007 (имена существующих FAB) + F-009 (корректные async states) могут быть маленькими независимыми исправлениями с тестами.
3. Overview/Edit и глобальный More — согласованный навигационный срез, с проверкой Back, глубоких ссылок, scope и прав.
4. Practice/Progress и Resume — следующий срез после сверки моделей, с тестами сохранения контекста. Не обещать непрерывность только новой оболочкой.
5. Распространить проверенные компоненты на остальные разделы; пройти расширенную матрицу устройств/ролей и лишь затем оценивать release readiness.
