# GH-186 — source review (read-only)

Scope: source-only review against the parent's fresh official issue read (OPEN; no comments). No tests were executed here. This report does not repair a defect, close the remote issue, or establish device acceptance.

## Finding

The issue's central gap is confirmed: source exports `createEventShare` and `revokeEventShare`, but no `listEventShares` callable. The app has create/revoke service wrappers but no list wrapper and no rendered inventory/revoke control. Existing roster share buttons mint and copy new links; they do not show live links already issued. The hardcoded share URL at `lib/screens/setlists/event_kit_editor_screen.dart:197` is present, but canonical/native URL policy is explicitly outside this issue review because GH-189 owns that blocker; do not change or prescribe a canonical URL here.

## Source evidence and existing guarantees

- Callable exports: `functions/src/events.js:371` creates; `:419` revokes; `:578` reads event view. No list export exists in the searched callable-export source. `revokeEventShare` requires auth, a tokenId, refuses demo accounts, reads only that share document, checks its stored scope via `requireScopeWriter`, and sets `revoked`/`revokedAt` (`:419-433`). It does not delete or mutate another token. Band scope requires a band writer; personal scope requires `uid === ownerUid` (`:185-194`). The list callable must use the same writer authorization and `refuseDemo`, for BOTH scope forms; a client-side filter is not authorization.
- Share document shape: create writes `tokenId`, exactly one scope, `setlistId`, `participantId`, `secretHash`, `revoked:false`, `expiresAt`, `createdBy`, `createdAt` (`:394-415`). Roster source in `loadSetlist` is available to resolve participant name/role/access without exposing uid (`:282-286`, `:384-392`). A response should be a deliberately projected metadata DTO (participant display name, role, sanitized granted areas, created time, expiry, revoked status, opaque revocation handle only if required); never return `secretHash`, raw secret/token, `createdBy`/uid, or arbitrary backing document fields.
- Expired links are not live; revoked links are not live. `resolveToken` rejects revoked and expired entries, but allows entries with no `expiresAt` for pre-expiry legacy links (`functions/src/events.js:338-364`). The admin inventory should distinguish revoked/expired from live rather than make either look revocable/live by accident. The request says every live link; whether expired/revoked history appears in the list is a product decision.
- Exact callable tests present: `creates, claims, views and revokes a personal share with exclusive scope fields`; `denies non-owners management and strangers access`; `denies demo accounts on every personal write path`; `stores only a hash, never the secret`; `stops working once revoked`; `stops working once expired`; `fails an expired link and a garbage link identically`; `keeps working when the document predates expiry`. These establish relevant behavior by assertions in source, not as tests run for this review. No current exact test asserts two links remain isolated when one is revoked, nor listing/projection/pagination.
- Current service methods: `createShare` sends `createEventShare` (`lib/services/event_share_service.dart:261-274`), `revokeShare` sends `revokeEventShare` (`:276-277`), and `getEventView` (`:281-294`). There is no list API or list DTO. Existing service test names include `personal event callables send ownerUid and omit bandId`, `createShare calls createEventShare and returns the raw token`, and `revokeShare calls revokeEventShare with the tokenId` (`test/services/event_share_service_test.dart:168-204,219-270`). None tests list.
- Editor: `_share` creates/copies and reports errors (`lib/screens/setlists/event_kit_editor_screen.dart:172-209`); roster controls render only when `_isMember` (`:277-321`). There is no link inventory or revoke UI. The editor already identifies band/personal scope via `bandId` and `ownerUid` and gates roster management; reuse the existing screen, Riverpod service provider, and Mono Pulse styling, not a new management architecture.
- Existing widget test names include `personal owner shares with free-form people without band members` and parameterized `share analytics respects $scenario` (`test/screens/setlists/event_kit_editor_test.dart:98-100,198-206`). These cover link creation/copy and role visibility/error edges, not inventory or revoke.

## Bounded implementation order: production/test pairs

1. Callable metadata-only list + callable tests, first. Add `listEventShares` in `functions/src/events.js`. Input is one validated `bandId` or `ownerUid` plus `setlistId`; require auth, refuse demo, and require the same scope writer as revoke. Query only that event's shares (Firestore is a global `eventShares` collection today, so scope/setlist filtering must be server-side and pagination must not accidentally return other events). Resolve current roster metadata and sanitize access; omit missing roster participants safely. Return an explicit allowlist DTO, no token, secret/hash, uid, or creator identifier. Bound work: use cursor pagination with a fixed maximum page size and `hasMore`/cursor (or another provably complete bounded strategy); do not silently truncate while claiming “every live link.” Define how clients enumerate all pages and how concurrent changes affect completeness. Treat missing `expiresAt` as legacy-live, and expose revoked/expired status explicitly. Tests: exact band-writer and personal-owner success; ordinary member/non-owner/unauthenticated/demo denial; cross-event isolation; name/role/access projection; no hash/token/uid leakage; revoked/expired and missing-expiry legacy classification; page boundary plus complete multi-page traversal/no duplicates. Preserve the source's current semantics for legacy links.
2. Flutter transport + service tests. Add a minimal metadata model/decoder and `listShares` wrapper in `lib/services/event_share_service.dart`, matching existing `_call` null stripping and provider pattern; add revoke scope only if the backend contract requires it (the current revoke accepts just tokenId and authorizes from stored scope). Tests assert callable name/arguments, DTO projection, paging/cursor forwarding, malformed/empty-safe decoding, and no accidental token-bearing fields. Reuse the existing `CallableInvoker` seam.
3. Rendered editor inventory/revoke + widget tests. In `event_kit_editor_screen.dart`, load all pages for the current scope, show each live link's person/name, role, granted areas and created timestamp, and call existing revoke then refresh/remove only that entry. Use current provider/Mono Pulse conventions. Cover loading, error with retry, empty, cancel/no-op, successful revoke, failed revoke/retry, and two entries where revoking one leaves the other visible. Cover band member and personal owner visibility; guest/area-editor/demo-role denial or absent controls. Do not expose raw tokens or hashes in UI. Avoid reminting or changing URL policy.

## Product uncertainty / acceptance

Named uncertainty: should the inventory show only currently usable links (recommended for the acceptance phrase “live link”), or also revoked/expired history with state? Also confirm whether pagination is a client-visible “load more” or transparently exhausted before presenting “every live link”; the acceptance requires completeness, so a silent page cap is insufficient. Created time needs a display timezone/format convention from the existing app if not already defined.

## Independent parent corrections / execution contract

- `functions/index.js:40-46` is the deployment export map: backend slice MUST wire `exports.listEventShares = events.listEventShares` there. This small required caller is explicitly added to the backend lease; omission would pass module tests but ship no callable.
- Band **writers** (admin/editor), not every band member, may manage links. Existing `_isMember` is not a writer check. Backend must enforce writer rights; UI slice must derive management rights from actual band/current-user providers and hide the new affordance for ordinary members, guests and demo accounts. Existing old roster-button parity belongs to GH-179, not a silent rewrite here.
- Inventory includes all issued records, with explicit `active`, `revoked`, `expired`, or `unavailable` state. Current roster supplies effective grants (not a historical snapshot); missing participants are shown as unavailable with empty grants, not silently dropped. Missing expiry remains legacy-live when participant exists; revoked takes precedence over expired. Return only tokenId (opaque revocation handle), participantId, name, role, sanitized access, createdAt, expiresAt, state; never backing identifiers/secrets or arbitrary fields. UI may group/filter states but must preserve every active link.
- Use fixed bounded pages ordered by document ID, event+scope filters applied on server, validated opaque document-ID cursor, `hasMore`/`nextCursor`, and no false total. Page iteration is eventually consistent, not a snapshot under concurrent creation; refresh restarts traversal. Listing is read-only and must neither mint nor revoke. No need to block the backend on history-display or timezone choices.
- URL centralization is explicitly retained as GH-186-URL, dependent on GH-189-L1 URL policy; it is NOT omitted from issue scope. Separate final GH-186-V retains two-link revocation isolation, combined permissions/client regressions, safe device roundtrip and owner closure. No release credit from this report.
