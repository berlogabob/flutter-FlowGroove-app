# UX-003-R — Songs card versus Setlist view

Accepted source review, 2026-10-25. CODE, not fresh DEVICE or human evidence.

## Confirmed branches

- `lib/screens/songs/songs_list_screen.dart:716-723`: card tap always calls `_navigateToEdit(song)`; explicit edit/delete callbacks alone are gated by canEdit. At `:967-973` this pushes `song`, id and Song extra, with no tab query. The helper name alone is not evidence of an editable destination.
- `lib/screens/setlists/setlist_view_screen.dart:130-148`: Edit Setlist is separately permission-gated, preserving id, optional bandId, storageScope and setlist extra. Song rows at `:279-286` have no editing callback; `_openSong` at `:327-337` passes tab=sheet and retains band context.
- Songs uses the app-wide canEditProvider (`songs_list_screen.dart:705`); Setlist uses personal or band-specific permissions (`setlist_view_screen.dart:59-80`). These are not equivalent role gates.

## Parent follow-through beyond worker scope

Worker correctly left the destination unverified because its three-file read window omitted routing. Parent resolved that named gap rather than inferring behavior from callback names:

- `lib/router/app_router.dart:61-79,390-393`: named song route forwards query tab unchanged to SongPageScreen, and preserves Song extra/band context.
- `lib/screens/songs/song_page_screen.dart:59-63`: absent tab defaults to Edit for non-demo users, but Sheet for demo users. Therefore the unconditional list callback does NOT prove that a read-only/demo account lands on Edit.
- `song_page_screen.dart:364-372,395-437`: band permissions can coerce Edit to Sheet; personal songs retain Edit-first behavior. Edit content embeds AddSongScreen only under its existing visibility/visited conditions. No save behavior or authorization bypass was exercised.

Thus source supports the historical regular-user Edit-first versus Setlist read-oriented asymmetry, with important demo/band exceptions. It does not establish confusion, data loss, accidental saves or a current installed-app result.
