# GH-187-U2-R — add-song selection blocker resolution

Status: U2 remains blocked for arbitrary add-song requests. This is a read-only source review; recommended design, not an approved owner decision; no implementation or execution claims.

## Evidence and boundaries

- `functions/src/events.js:578-599,610-665`: `getEventView` builds its payload from the caller’s event grant. Song documents are fetched only for song IDs already in the event order (`:623-635`); titles are projected and song details are included only with `songDetail` (`:636-656`). This is an event-scoped projection, not a library picker.
- `functions/src/events.js:802-818,898-923`: typed add is fingerprint-gated; acceptance checks the proposed song in `scopeRef(scope).collection("songs")` and rejects if absent. It currently offers no candidate discovery path.
- `firestore.rules:292-295`: band song reads require authentication and band membership. `lib/services/event_share_service.dart:12-19` documents why guests cannot directly read full event documents; the library restriction itself is in the rules; guest reads use a scoped callable instead. `firestore.rules:440-442` also limits suggestions subcollection reads to authenticated band members.
- `lib/screens/setlists/create_setlist_screen.dart:80-101,336-369`: the existing library picker reads either `songsProvider` or `bandSongsProvider` for setlist creation/editing. Its context is a signed-in setlist author, not an anonymous event guest; it is not reusable as guest authorization.
- `lib/services/event_share_service.dart:281-294,301-319`: existing public seams are `getEventView` and `submitSuggestion`; submission already carries `proposal`. `lib/screens/setlists/event_share_screen.dart:103-130` sends the draft, while `:431-459` and `:485-500` establish typed choice UI. Current rendered choices include note/remove/reorder but not add; the sheet’s selectable song labels come from event songs already projected into `view.songs` (`:457-460`).

## Source options

1. Smallest safe guest-facing source: an explicit, bounded event-published candidate list projected by the server into `getEventView`, separate from private library access. Candidates need only the public selection fields (stable scoped song ID, title and artist); no charts, private metadata, or unrestricted library query. The backend must verify a selected candidate is still published and belongs to the exact event scope when resolving. The source cannot be presumed to exist or be publishable today. Who may publish, what is published, revocation/visibility, and whether the event owner wants anonymous guests to choose from it require owner approval.
2. Authenticated authorized-owner/band-side selection: potentially use existing library reads/picker only after proving the signed-in user is authorized for that exact event scope. This preserves library privacy but does not fulfill an anonymous guest’s arbitrary add-song intent. Requiring login, changing the guest workflow, or allowing a helper to choose on the guest’s behalf are product/owner decisions, not safe assumptions.

Recommendation: approve or reject a minimal event-published candidate contract before U2 implementation. Do not substitute duplicate occurrence of an existing event song: that is not arbitrary add-song selection. Do not grant guests whole-library reads. If publication is not approved, retain add as unavailable and U2 stays blocked; note/remove/reorder remain accepted.

## Minimal privacy-preserving contract, if approved

Server projects only the explicitly published candidates for this event, capped and validated, under the existing event-view authorization; absence, denial, or truncation is explicit and never represented as a complete library. Candidate IDs are scoped opaque IDs, not inferred from titles. Submission carries the chosen candidate ID plus the existing typed add proposal/base fingerprint. Resolve rechecks authorization, scope, publication and song existence transactionally, then applies the existing stale-base and insertion-anchor checks. Omitted/unpublished, inaccessible, deleted, cross-scope, malformed or over-cap candidates fail closed; no candidate/song details are returned for rejected or inaccessible IDs. Do not change note semantics or prose execution.

Owner approval required: existence and meaning of “published”; who can publish/unpublish; candidate fields/cap and whether anonymous link holders may see them; whether personal-event owners and band owners get equivalent behavior; desired guest intent if no candidate is published. Implementable after approval: bounded server projection, proposal validation/revalidation, transport, selection UI, rejection tests. No access-model or permission expansion is implied here.
