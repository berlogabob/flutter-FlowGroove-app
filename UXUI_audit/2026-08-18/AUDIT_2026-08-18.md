# FlowGroove — Full UX/UI Audit & Measurable Fix Plan

**Date:** 2026-08-18 · **Build audited:** 0.23.0+361 (local working tree, ahead of GitHub main 0.20.1+353)
**Method:** full static code audit of all 24 core user journeys (tap-cost counted from code), design-system conformance sweep (grep-verified counts), WCAG-referenced accessibility sweep, regression verification of both July audits (AUDIT.md P-items + 2026-07-18 F-001…F-021), behavior-bug hunt (each finding verified at file:line, go_router 17.3.0 source consulted for navigation semantics), HEART instrumentation audit of `analytics_service.dart` / `analytics_events.dart` call sites, and visual review of device screenshots.
**Not covered live:** no on-device/browser walkthrough this pass (offer stands — a Chrome run on flowgroove.app can re-measure the tap counts empirically).

---

## Overall Impression

FlowGroove 0.23 is a far more disciplined app than the one audited in July — 15 of 21 July findings are verifiably fixed, the bottom-first navigation is consistently implemented, and the Rehearsals flow is now one of the best-designed surfaces in the app. But the audit found **three broken promises that outrank any polish issue**: band renames silently save to a location nothing reads (data loss), the "Discard changes?" guards never fire for the app's own Back button (data loss), and the README-advertised per-gig key/BPM override does not exist in the UI — while the metronome's auto-save actively *rewrites the song's global BPM* when you nudge tempo for a gig. On top of that, the navigation paradigm has quietly created a "menu tax": on the setlist view screen — the screen a musician opens *at the gig* — there are **zero visible actions**; all five live behind Menu.

The HEART problem is now specific: after the Aug-11 repair the pipeline works, but three high-value events are inflated by fire-on-rebuild bugs, the perform moment (the app's core value) emits no events at all, there is no crash reporting, and no goals/targets/dashboards exist. This report ships both: the missing framework and the instrumentation fix list.

## What Works Well (keep these)

- **1-tap perform paths via pinned card quick-actions** — song card → Metronome preloaded with tempo is a single tap (`song_card_actions.dart:255-262`); setlist card → full metronome queue in 2 taps. This is the app's best interaction and the model the rest should follow.
- **Rehearsal detail screen** — voting chips, best-slot highlight, blocker names, confirm, .ics export: the most action-dense screen has *everything visible* and needs no menu (`rehearsal_detail_screen.dart`). It inverts the menu-first pattern — and is better for it.
- **Bottom-first navigation fundamentals** — 0 interactive controls in the top 15% of the screen, ≥48px nav targets, consistent `[Back | title | Menu]` chrome, in-app Back on web. The Fitts goals from July hold.
- **Add-song autofill** — 5 taps from Songs root to a fully-populated saved song, with duplicate detection (≥90% match dialog) and provenance links.
- **Empty states** — 12 screens use the shared `EmptyState` with purposeful copy; the rehearsals and band empty states teach the domain.
- **July remediation quality** — fixes are annotated in code with finding IDs (F-004, F-007, F-013…), bottom paddings, black-on-orange FABs, titled sheets, 48dp metronome targets, seconds-precision practice stats. This is how remediation should look.

## 1 · Critical Findings (fix before anything else)

Severity: 🔴 data loss / broken promise / trust-killer · 🟡 significant friction or confusion · 🟢 polish.

### 🔴 C-1 · Band rename & description edits vanish into a write-only collection
Renaming a band from The Band screen menu ("Edit Band Name" / "Edit Description") or saving About-screen edits calls `saveBand(…, uid:)`, which writes **only** to `users/{uid}/bands/{id}` (`firestore_service.dart:86-95`; call sites `the_band_screen.dart:363,437`, `band_about_screen.dart:712`). Every band surface **streams the global `bands` collection** (`firestore_band_repository.dart:98`), and no Cloud Function syncs the personal copy back. The user sees "updated successfully", then the old name everywhere; About-screen edits visibly revert on the next stream tick (`band_about_screen.dart:65-75`). Only the `edit-band` route works (it uses the dual-write `saveBandBatch`, `create_band_screen.dart:122`).
**Fix:** route all three paths through `saveBandBatch` (or a Cloud Function for non-admin field rules). **Measure:** `band_updated` event on the fixed path; support contacts about "rename didn't work" → 0.

### 🔴 C-2 · The app's own Back button bypasses every "Discard changes?" guard
Create/Edit Setlist and Create/Edit Band guard dirty state with `PopScope(canPop: !_hasUnsavedChanges)` + confirm dialog (`create_setlist_screen.dart:546-558`, `create_band_screen.dart:238-251`). But the shell's Back calls `context.pop()` (`main_shell.dart:259-265`) → go_router 17's `delegate.pop` → `NavigatorState.pop()` directly, which **never consults `canPop`** (verified against go_router 17.3.0 source). The dialog only ever appears for the Android system-back gesture; on web it can *never* appear. Net: the visible Back button silently discards dirty forms. The repo itself works around this twice (`join_band_screen.dart:190-215`, `song_editor_screen.dart:233-238`), confirming the mechanism.
**Fix:** `_handleBack` should call `Navigator.maybePop` on the innermost navigator (or route per-screen `onBack` through the dirty check). **Measure:** add `form_discarded {screen, guarded}` event; guarded-discard rate ≈ 100% of discards.

### 🔴 C-3 · Rehearsal editor has no guard at all — 14 taps of planning lost to one Back
`RehearsalEditScreen` (N time slots via 5 taps each, member roles, deadline, venue, notes) has **no PopScope, no dirty tracking, no autosave** — Back discards everything instantly (whole file; save only at `rehearsal_edit_screen.dart:337-346`). This is the app's longest form (13-14 taps minimum) and its least protected. Its Save button is also the only major form CTA *not* pinned (it scrolls, `:337-346`).
**Fix:** same guard as C-2's fixed version + pin the Save bar (`PrimaryActionBar` like setlist/band forms).

### 🔴 C-4 · Per-gig key/BPM overrides don't exist — and the workaround corrupts the song
README line 91 advertises "Drag-and-drop setlists with per-gig overrides for key, BPM, notes." The model field exists (`SetlistAssignment.keyOverride`, `setlist_assignment.dart:11,20`) but **no screen reads or writes it** — editor and view render the song's global key/BPM as static badges (`create_setlist_screen.dart:892-918`, `setlist_view_screen.dart:209-238`). Worse: the natural workaround — nudging BPM in the metronome during rehearsal — **debounce-auto-saves to the global song** (`metronome_screen.dart:125-130`), permanently rewriting `ourBPM` for every setlist and bandmate.
**Fix:** (a) make metronome BPM changes for a queued setlist song write the setlist override (or ask), never the song, and (b) add an override editor to the setlist song row — or remove the claim from the README/store copy until built. **Measure:** new `gig_override_set` event; `song_edited` events with `fields_changed=ourBPM` originating from metronome → 0.

### 🔴 C-5 · Undo is a lottery: one snackbar destroys another, and songs get none
All delete-undo flows are **immediate-delete-then-restore**; the only restore path is a 5s snackbar. `showAppSnackBar`/`showGlobalSnackBar` call `hideCurrentSnackBar()` before every show (`snackbar.dart:16,51`) — so deleting a second setlist (or *any* subsequent toast, e.g. "Copied links") within 5s **permanently destroys the first Undo**. Setlist delete is also swipe + no confirm (`unified_item_list.dart:68-78` — delete IS the confirm). Meanwhile songs get a confirm dialog but **no undo at all** (`songs_list_screen.dart:1006-1011`) — the opposite tradeoff on the more valuable object (a song carries lyrics, structure, Lab history).
**Fix:** defer actual deletion until snackbar expiry (or queue action-snackbars instead of replacing); give song delete the same undo. **Measure:** `undo_shown`→`undo_used` ratio becomes reliable; support reports of lost items → 0.

### 🔴 C-6 · Setlist manual reorder is a complete no-op
Card drag-reorder on the Setlists tab and Band setlists list animates, then snaps back: `_manualOrder` is initialized nowhere and `_handleReorder` early-returns while it is null (`setlists_list_screen.dart:38,84-105`; `band_setlists_screen.dart:41,100-119`). Even if it ran, the "save" writes whole setlist docs that contain **no order field** into an unordered query — N clobbering writes persisting nothing (band variant would overwrite bandmates' concurrent edits).
**Fix:** either remove "Manual" sort from these lists, or implement it (order field + init `_manualOrder` from current sort). **Measure:** reorder action persists across restart (integration test); zero clobbering writes.

### 🔴 C-7 · Dead back arrow on Create Account
Login navigates to Register with `context.goNamed('register')` — a *replace* — and Register's arrow calls bare `context.pop()` with nothing to pop → go_router throws `GoError`, swallowed silently (`login_screen.dart:375`, `register_screen.dart:137-140`). First-session users tap a dead button on the second screen they ever see. (Register is also one of two forms with no Enter-to-submit and its password checklist never updates while typing — `register_screen.dart:95-103,184-200`.)
**Fix:** `context.canPop() ? context.pop() : context.goNamed('login')`; add `onChanged` rebuild + `onFieldSubmitted`. **Measure:** signup completion rate (funnel below).

### 🔴 C-8 · Infinite spinners on resolver errors; refresh teleports users
`BandRouteResolver`/`SetlistRouteResolver` render an eternal `CircularProgressIndicator` when the stream errors or the id is gone (`app_router.dart:845-857,904-914`); the Song Page does the same for dead song ids (`song_page_screen.dart:79-90`). On web, refreshing an audio note **lands you on the Recorder list with no explanation** (`app_router.dart:656-668`); the Event Kit editor has no route at all — refresh loses it entirely (pushed imperatively from 3 call sites).
**Fix:** error+retry state in resolvers; id-based lookup for audio notes; a real route for Event Kit. **Measure:** `screen_view` of error screens; rage-refresh sequences in GA4 path exploration.

### 🟡 C-9 · Demo mode lets users do work that can never save
The demo account can open the Recorder (no `canEdit` gating in `recorder_screen.dart`) and record a take whose save is rejected by Firestore rules (`firestore.rules:34-36,304`) — work lost. Root-pushed tools cover the shell, so the "Demo mode" banner isn't even visible there (`main_shell.dart:121-123`). Deep-linking to `/main/songs/add` lets demo fill the whole form before failing.
**Fix:** gate write affordances on `canEditProvider` + show the banner (or a read-only chip) on tool screens.

### 🟡 C-10 · Songs-list stream error mutates state during build
`when(data:)` → `_clearError()` (setState) and `error:` → `_handleStreamError` (setState + provider write) run synchronously inside `build` (`songs_list_screen.dart:660-674,399-412`) — an assert-crash in debug, an illegal-mutation smell in release (one-frame-late banners, spurious rebuilds).
**Fix:** derive the banner from the AsyncValue; move mutations to `ref.listen`.

### The four structural taxes behind the numbers

1. **The menu tax.** Every contextual action costs `Menu → row` (2 taps) plus a discovery problem: the only cue that actions exist is an 8px orange dot with no semantics. Two screens have **zero** visible actions (SetlistView, BandAbout); the Song Page hides 5–7 actions including both exports. The `menu_opened` event you already log is the perfect measure: **menu_opened per session should fall** as the top action per screen moves into the bar's unused `primaryAction` slot.
2. **Card-tap lands on Edit.** The highest-frequency object-open in the app (song card) defaults to the editing surface (`_SongTab.edit`), not the performing surface. Performers pay +1 tap every time; accidental-edit risk concentrates exactly where fingers land. Default to Sheet (or last-used tab).
3. **Hidden gestures with no affordance.** Swipe-to-delete and long-press-to-reorder exist nowhere in visible UI, in help, or in onboarding (which doesn't exist — D-5). Combined with C-5's fragile undo, the swipe is a trap.
4. **Collapsed-by-default forms.** All six metadata sections of the song form start collapsed (`song_form.dart:186-311`) — every metadata edit pays +1 expand tap, and autofill writes into invisible fields (only a snackbar hints it happened).

### 7.1 The framework (Goals → Signals → Metrics)

North star: **bands that prepare their next gig in FlowGroove every week.**
